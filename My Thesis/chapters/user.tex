\chapter{User Documentation}

\section{Short Problem Statement}
\textit{A Task for Two} is a cooperative two-player puzzle application in which each player has incomplete local information. Neither player can solve the puzzle independently, as each side controls a die that contributes to the other player’s missing equation value.

The game addresses coordinated remote puzzle solving, where both players must create or join the same session, communicate observed values, perform synchronized actions, and complete a shared objective. The level is completed only when both sides maintain the correct puzzle state long enough for the barrier to open.

\section{Brief Method Overview}
The implemented method combines asymmetric puzzle information with synchronized multiplayer state updates. Each side receives one equation with a hidden value, while each player can rotate one die, requiring communication to solve the counterpart’s missing value.

Session connectivity is managed through Unity Relay and host/client Netcode startup. Each player controls only their own player object, while puzzle state, die lock status, and end-state triggers are synchronized. The solve algorithm requires continuous correctness for a hold duration, preventing accidental success from rapid interactions.

The user flow is linear: session setup in the main menu, puzzle collaboration in gameplay, followed by either a victory end screen or a connection-lost recovery state if the host disconnects.

\section{Installation and Startup}
\begin{enumerate}
\item Open the release page: \url{https://github.com/hassan-afifi/A_Task_For_Two/releases/tag/v2.5.8}
\item In the \textbf{Assets} list, download \texttt{A\_Task\_For\_Two.zip}.
\item Extract \texttt{A\_Task\_For\_Two.zip} to a local folder.
\item Open the extracted folder and run \texttt{A Task For Two.exe}.
\item In the main menu, enter a player name, then choose \textit{Create Game} (host) or \textit{Join Game} (client with join code).
\end{enumerate}

\section{Session Validation}
The menu layer applies deterministic input validation before allowing session operations:
\begin{itemize}
\item Player name must contain at least one letter.
\item Join code must contain exactly six characters after trimming.
\item Join code is normalized to uppercase before join request.
\item Create/Join buttons are interactable only when corresponding validation rules pass.
\end{itemize}

These checks reduce invalid network requests and provide immediate feedback before Relay operations start.

\subsection*{Use Case Diagram Description}
Figure~\ref{fig:use-case-diagram} summarizes user-facing behavior from session setup to terminal outcomes. The primary actor is \textit{Player}, specialized as \textit{Host Player} and \textit{Client Player}. Host and client roles follow different entry paths (\textit{Create Session} vs \textit{Join Session}), both converging at \textit{Connect via Relay} and then \textit{Start Game}.

The use cases represent the complete operational path:
\begin{itemize}
\item setup actions (set player name, choose character, configure settings),
\item session actions (create or join session, connect via Relay, start game),
\item runtime actions (control player, pause/resume game, interact with puzzle, solve puzzle),
\item terminal actions (complete level and show end screen, or lose host connection and show connection-lost screen).
\end{itemize}

\newpage

\subsection*{Relationship Explanation}
The relationships describe dependency and specialization semantics:
\begin{itemize}
\item \textit{Host Player} and \textit{Client Player} are specialized forms of the common \textit{Player} actor.
\item Both session-entry flows (\textit{Create Session}, \textit{Join Session}) converge at \textit{Connect via Relay}.
\item \textit{Start Game} branches into gameplay control and pause/resume behavior.
\item The gameplay chain is modeled with includes: \textit{Control Player} $\rightarrow$ \textit{Interact with Puzzle} $\rightarrow$ \textit{Solve Puzzle} $\rightarrow$ \textit{Complete Level}.
\item Terminal behavior is explicit in two paths: completion leads to \textit{Show End Screen}, while leaving the session leads to \textit{Handle Connection Loss} and then \textit{Show Connection Lost Screen}.
\end{itemize}

Overall, the model captures the complete user interaction lifecycle, from session initialization to termination states.
