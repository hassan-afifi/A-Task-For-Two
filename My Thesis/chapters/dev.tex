\section{Detailed Problem Specification}
The implemented software is a two-player online cooperative puzzle prototype. The core technical objective is to guarantee consistent multiplayer puzzle state while preserving clear separation between networking, gameplay rules, and UI concerns.

The practical engineering challenge is not only puzzle generation, but coordinated runtime behavior across multiple subsystems:
\begin{itemize}
\item reliable host/client session initialization,
\item authority-controlled state mutation,
\item predictable user input flow during gameplay and menu overlays,
\item deterministic puzzle progression and lock logic,
\item robust end/disconnect transitions.
\end{itemize}

\newpage

\subsection*{Functional Requirements Breakdown}
The game loop is implemented through the following functional requirements.
\begin{enumerate}
\item Two participants establish an online session by host creation and join-code-based client connection.
\item Both participants load the same gameplay scene and own only their local player object.
\item Each participant receives one local equation view with partial information.
\item Each participant rotates one interactive die that contributes to the counterpart's missing value.
\item Puzzle solved state is accepted only after continuous correctness hold.
\item Solved puzzle raises a barrier and enables level completion.
\item Entering the end trigger transitions all participants to a shared end screen.
\item Disconnect before victory transitions the affected participant to a connection-lost flow.
\end{enumerate}

\section{System Overview}
The application is implemented in Unity with C\# scripts, Netcode for GameObjects replication, and Relay transport integration \cite{unity_ngo_networkvariable_docs,unity_ngo_rpc_docs,unity_relay_docs}. Runtime responsibilities are intentionally split into four cooperating layers:
\begin{itemize}
\item \textbf{Session and networking layer}: menu validation, relay create/join, net startup, scene transition.
\item \textbf{Gameplay layer}: player movement/interaction, die animation, puzzle solve state, barrier/open flow.
\item \textbf{UI and settings layer}: menu panels, pause/options behavior, persisted user preferences.
\item \textbf{Verification layer}: edit-mode and play-mode behavior tests.
\end{itemize}

\newpage

\subsection*{Runtime Lifecycle}
The runtime sequence follows a deterministic system-level flow:
\begin{enumerate}
\item Main menu validates name/code input and enables create/join actions.
\item Host allocates Relay session; client joins by code.
\item Netcode starts host/client and transitions to gameplay scene.
\item Local owner components activate input, camera, and movement.
\item Participants interact with puzzle dice through ownership-safe raycast actions.
\item Server-authoritative logic evaluates the hold condition and updates the shared puzzle state accordingly.
\item Barrier opens and end trigger broadcasts shared end-screen state.
\item Disconnect before victory redirects to connection-lost recovery UI.
\end{enumerate}

This separation prevents network transport concerns from propagating into UI components and keeps gameplay logic independent of menu panel implementation details.

\section{Architecture Rationale}
\subsection*{Design Principles}
The architecture follows a separation-of-concerns strategy to isolate session transport, gameplay rule evaluation, and user-interface behavior. This design is necessary because host/join flow, replicated puzzle state, and menu interactions operate concurrently within the same runtime lifecycle. Clear responsibility boundaries therefore reduce cross-module coupling during iterative development.

A server-authoritative model was selected for gameplay-critical state transitions. Puzzle progression, solve validation, die lock state, and terminal flow triggers are committed through server-authoritative logic and then propagated through replicated state containers and RPC events. This avoids conflicting client-side writes and guarantees a single canonical multiplayer state.

Lifecycle operations were intentionally centralized. Input validation, Relay initialization, transport configuration, scene transition, and shutdown handling are orchestrated by dedicated session/menu components rather than distributed across gameplay scripts. This improves operational predictability and simplifies debugging of create/join/return paths.

Fail-fast initialization checks were also adopted for components with dense serialized dependencies. Early detection of missing references is preferable to silent partial behavior during runtime, and it improves repeatability in both automated and manual validation workflows.

\subsection*{Entity-Component Architecture in Unity}
The implementation follows Unity's component-based architecture \cite{unity_components_docs}. Runtime entities are represented as \texttt{GameObject} instances, while behavior is composed through attached components (for example, \texttt{PlayerInputHandler}, \texttt{PlayerMovement}, \texttt{PlayerInteractor}, and \texttt{PlayerVisuals} on player objects).

This composition strategy was selected to keep responsibilities modular, avoid inheritance-heavy designs, and support iterative prefab-based assembly. Multiplayer-specific behavior is integrated through \texttt{NetworkBehaviour} components for replicated state and authority-aware execution, while non-networked concerns remain in regular \texttt{MonoBehaviour} components \cite{unity_monobehaviour_docs}.

The resulting entity-component style is well suited to the thesis scope: explicit runtime composition, maintainable subsystem boundaries, and direct compatibility with the selected Unity Netcode workflow.

The resulting architecture prioritizes correctness, observability, and maintainability over feature breadth. This tradeoff is appropriate for the thesis scope and provides a stable base for future extensions. The combination of component-based composition, authoritative state management, and layered module separation enables predictable runtime behavior and supports iterative development.

\subsection*{Module Purpose and Responsibilities}
Figure~\ref{fig:module-diagram} presents a high-level module view of the system architecture, abstracting implementation details into responsibility-driven layers.

\begin{itemize}
\item \textbf{Presentation Layer}: provides all user-facing interaction surfaces, including session/menu actions, in-game HUD feedback, and terminal overlays (pause, end, and recovery). Its primary role is to collect user intent and render current system state without owning multiplayer state transitions.
\item \textbf{Gameplay Layer}: encapsulates the interactive game domain, including player control, puzzle rule evaluation, and game-flow transitions (start, solve, finish, fail). It translates user actions into rule-driven outcomes.
\item \textbf{Networking Layer}: coordinates session lifecycle, shared state replication, ownership boundaries, and authoritative validation. This layer guarantees that multiplayer-critical decisions are evaluated consistently and published as replicated state.
\item \textbf{Persistence Layer}: stores device-local preferences and profile-related values used across sessions, such as options and player identity settings.
\item \textbf{Verification Layer}: defines automated quality gates through edit-mode and play-mode tests. It validates isolated logic, runtime interactions, and critical end-to-end behavior paths.
\item \textbf{Unity Platform and Services}: supplies foundational runtime and service infrastructure, including engine execution, Netcode replication APIs, Relay transport, authentication services, local storage, and the Unity Test Framework.
\end{itemize}

\subsection*{Interaction Flow and Design Intent}
The dependency direction in Figure~\ref{fig:module-diagram} is intentional and reflects the runtime control path:
\begin{itemize}
\item Presentation triggers session and gameplay actions, but networking and gameplay modules own state mutation logic.
\item Gameplay modules request authoritative puzzle validation through the networking layer, which then publishes replicated state.
\item Session lifecycle operations (create, join, leave) are delegated to Relay and authentication services rather than implemented in UI modules.
\item Persistent settings are written and restored through a dedicated persistence boundary, keeping local configuration separate from replicated multiplayer state.
\item Runtime behavior executes on Unity engine services, while verification modules depend on Unity Test Framework for repeatable automated validation.
\end{itemize}

This design ensures responsive user interaction, consistent multiplayer behavior, and explicit subsystem boundaries that support maintainability, testing, and future extension.

The project is partitioned into script groups by responsibility:

\item \textbf{Player control/presentation}: \texttt{PlayerInputHandler}, \texttt{PlayerMovement}, \texttt{PlayerInteractor}, \texttt{PlayerVisuals}, \texttt{PlayerAudio}, \texttt{CharacterAnimation}, \texttt{CharacterSelection}.
\item \textbf{Puzzle domain}: \texttt{PuzzleController}, \texttt{DieClickAnimate}.
\item \textbf{UI widgets}: \texttt{OptionsMenu}, \texttt{SliderHelper}, \texttt{AnimatedToggle}, \texttt{GenderToggle}, \texttt{DropdownHelper}, \texttt{HudStats}, \texttt{MenuSfx}.

Two design rules are applied consistently:
\begin{itemize}
\item \textbf{Authority rule}: gameplay mutations that affect shared state are validated and committed through server-authoritative logic.
\item \textbf{Fail-fast setup rule}: major runtime components validate serialized references during startup and throw explicit setup errors when required references are missing.
\end{itemize}

This approach reduces hidden coupling and improves runtime observability and diagnosability.

\section{System Modules}
This section describes the main runtime modules and their responsibilities within the system architecture.

\subsection*{Session and Networking Module}
This module handles menu-triggered session lifecycle from initial input to synchronized scene transition.

\textbf{Main responsibilities:}
\begin{itemize}
\item \texttt{MainMenu} validates user input (name with at least one letter, join code length of six).
\item \texttt{GameSession} stores persistent session identity values (name and selected character) and current join code.
\item \texttt{RelayManager} initializes Unity Services/authentication, allocates or joins Relay, configures transport, starts host/client, and triggers scene load \cite{unity_authentication_docs,unity_relay_docs}.
\item An ownership correction step is applied if player object authority is not assigned during initial connection (implemented in \texttt{RelayManager.EnsureOwner}).
\item \texttt{MenuActions.StopNet} centralizes network shutdown before scene return or application exit.
\end{itemize}

\textbf{Design rationale:} transport configuration and network startup remain outside gameplay scripts, so puzzle/player components are not coupled to relay allocation details.

\subsection*{Player Module}
The player module is explicitly decomposed into input capture, movement simulation, world interaction, visual replication, and movement audio.

\textbf{Input and movement details:}
\begin{itemize}
\item \texttt{PlayerInputHandler} captures action-map state and gates input by pause/disconnect state.
\item \texttt{PlayerMovement} applies first-person movement and camera look using local-owner execution.
\item Spawn positions are role-based (host side and client side are separated).
\item Movement parameters include walk speed, sprint multiplier, crouch speed multiplier, gravity scaling, jump power, and cooldown.
\end{itemize}

\textbf{Interaction and presentation details:}
\begin{itemize}
\item \texttt{PlayerInteractor} performs center-screen raycast interaction with a fixed max distance.
\item \texttt{PlayerVisuals} replicates selected character and player name; local body mesh is hidden from owner view via layer assignment.
\item \texttt{PlayerAudio} synchronizes movement loop and landing cues to non-owner peers through targeted RPC dispatch.
\item \texttt{CharacterAnimation} maps movement state to animator parameters and jump trigger.
\end{itemize}

\subsection*{Puzzle Module}
Puzzle behavior is implemented by \texttt{PuzzleController} and \texttt{DieClickAnimate}.

\textbf{Puzzle state model:}
\begin{itemize}
\item Two local displays hold equation data: missing value, two known values, and sum.
\item The authoritative puzzle state is encapsulated within \texttt{NetworkPuzzleState} and distributed through \texttt{NetworkVariable}.
\item Target mapping is cross-linked: die 1 solves equation 2 missing value and die 2 solves equation 1 missing value.
\end{itemize}

\textbf{Generation and solve algorithm:}
\begin{itemize}
\item Symbol values are generated in the \([0,9]\) range.
\item Equation-pair generation explicitly rejects the both-missing-zero case.
\item Solve acceptance requires both dice to be correct and not rolling for a continuous hold duration.
\item Any wrong value or ongoing roll immediately resets hold progress.
\item On solve commit, both dice are locked and barrier animation starts.
\end{itemize}

\textbf{Timing constants in implementation:}
\begin{itemize}
\item die roll phase duration: \texttt{0.28s},
\item solve hold requirement: \texttt{0.82s},
\item barrier raise duration: \texttt{1.28s},
\item barrier raise offset: \texttt{4.82} local units.
\end{itemize}

\subsection*{UI and Options Module}
The options layer applies runtime configuration and persistence for display, controls, audio, crosshair, and HUD widgets.

\textbf{Implemented option behavior:}
\begin{itemize}
\item display mode switching between windowed/borderless/fullscreen,
\item resolution list rebuild by mode (fullscreen filtering by aspect ratio),
\item quality level selection,
\item owner camera FOV and sensitivity update,
\item five mixer-controlled audio channels,
\item crosshair size/color updates,
\item FPS/ping/clock widget visibility toggles.
\end{itemize}

All changes are persisted through \texttt{PlayerPrefs} \cite{unity_playerprefs_docs}. The same options logic is reused from both main-menu and pause-menu contexts.

\section{Design Decisions}
The implementation incorporates several design decisions derived during development and testing.

\subsection*{Continuous Solve Validation}
A key gameplay correction was enforcing continuous correctness during the solve hold duration. The final logic resets hold progress immediately when values become wrong or dice are still rolling, preventing delayed solve acceptance after transient correctness.

\subsection*{Network Lifecycle Cleanup}
A duplicate \texttt{NetworkManager} issue after returning to menu was addressed by centralizing network shutdown and object destruction in \texttt{MenuActions.StopNet}. This keeps menu return/exit paths consistent.

\subsection*{Session Initialization Order}
\texttt{GameSession} uses explicit early execution order to reduce startup race conditions with menu components that read session data during enable/awake phases.

\subsection*{UI Input Module Consistency in Tests}
Play-mode tests explicitly ensure EventSystem compatibility with the active Input System setup to avoid legacy module mismatches during automated UI interaction checks.

\section{Error Handling}
Error handling is implemented through explicit guard logic across startup, session actions, and shutdown paths.

\subsection*{Startup and Setup Validation}
Core runtime components apply fail-fast setup validation for required serialized references. Missing critical references are surfaced immediately during initialization to prevent partial execution with undefined behavior. This approach improves fault localization and reduces debugging time during both development and testing.

\subsection*{Session Input Guards}
Session operations are protected by deterministic menu-side validation before network calls are issued. Name and join-code constraints are validated locally, and create/join actions remain disabled until input is valid. These guards reduce invalid create/join attempts and keep session lifecycle behavior predictable.

\subsection*{Safe Shutdown and Return Flow}
Menu return and exit operations use centralized shutdown through \texttt{MenuActions.StopNet}. Network manager teardown and related cleanup are applied before scene changes, which avoids duplicate manager instances and stale network state across repeated session cycles.

\section{Fault Recovery}
Recovery behavior covers runtime interruption scenarios and their verification paths.

\subsection*{Disconnect Recovery Flow}
Unexpected session interruption is handled through the dedicated \texttt{ConnectionLost} path. Disconnect callbacks trigger controlled recovery UI instead of allowing gameplay to continue in a degraded network state. This keeps failure behavior explicit and prevents ambiguous user-facing outcomes.

\subsection*{Recovery Path Verification}
Recovery behavior is verified through both automated and manual validation. Play-mode tests cover menu/session transitions, disconnect-related flows, and runtime cleanup-sensitive paths, while edit-mode checks cover local guard logic and utility behavior. Manual host/client runs further confirm disconnect recovery and return-to-menu reliability under practical conditions.

\section{Testing Methodology}
Testing is implemented with Unity Test Framework \cite{unity_test_framework_docs} in two execution modes.

\subsection*{Test Design Policy}
The applied test design policy is:
\begin{itemize}
\item one focused test method per targeted public behavior,
\item behavior and branch verification over object-existence-only checks,
\item explicit naming convention for test readability,
\item setup/teardown isolation to prevent cross-test state pollution.
\end{itemize}

\subsection*{Edit Mode vs Play Mode Split}
\begin{itemize}
\item \textbf{Edit mode} is used for fast validation of isolated logic (input consumption, option mapping/clamping, persistence, static utility behavior, UI helper behavior).
\item \textbf{Play mode} is used for runtime orchestration, coroutine timing, scene transitions, network-aware components, and owner/non-owner behavior.
\end{itemize}

\newpage

\subsection*{Isolation Techniques}
To preserve repeatability, tests use explicit cleanup and deterministic scaffolding:
\begin{itemize}
\item \texttt{PlayerPrefs.DeleteAll()} in setup/teardown for persistence isolation,
\item object cleanup helpers to destroy transient game objects and components,
\item network manager cleanup between tests,
\item event-system setup compatible with Input System UI behavior \cite{unity_input_system_docs}.
\end{itemize}

\subsection*{Manual Testing Method}
Manual testing complements automated tests in scenarios where real-time multiplayer timing, role asymmetry, and user coordination are central to correctness.

\textbf{Execution protocol:}
\begin{itemize}
\item Start separate host and client runtime instances from a clean menu state.
\item Execute a fixed scenario checklist from session creation to terminal flow.
\item Verify outcomes on both host and client views, not only on the local initiating side.
\item Include negative-path runs (invalid input, forced disconnect, menu return and re-entry).
\item Repeat key scenarios after returning to main menu to confirm lifecycle cleanup.
\end{itemize}
